# Rust and Bun rewrite plan

This experiment explores replacing Juiced's serving core with Rust and its console tooling with Bun. It is isolated from the concurrent platform work. The current C++ service remains the release implementation.

The requested direction is confirmed by the November 10 user request. The module layout and sequence below are implementation proposals. They do not supersede the product scope in [the platform plan](../PLATFORM-PLAN.md).

## Product and design boundary

Juiced remains a model appliance for external clients. Keep artifact identity, execution profiles, Disabled / On demand / Hot policies, observed worker state, temporary service tests and bounded diagnostics. Retain the eight console destinations in the eventual migration. Do not introduce saved conversations, a general agent framework or model-weight conversion. Barista is the sole optional operator-assistant feature. Its required B0-B4 work follows the upstream P0-P6 sequence below. It is not deferred to the optional scale phase.

The new console uses the existing T3-derived charcoal palette, Inter, compact buttons, sidebar navigation, aligned model rows and a persistent inspector. Native HTML controls replace the dependency-heavy primitive stack. Plain CSS owns tokens and component variants. React and React DOM are the only runtime npm dependencies. Bun owns installation, bundling, development serving and tests. TypeScript and type declarations are development dependencies. No Tailwind, Vite, router, query library, icon package, drag library or markdown renderer is required for this slice.

The first operator journey is: connect to the isolated service, inspect the model list, select a model, review policy and actual state, save policy with a revision guard, load or unload when eligible, run a temporary chat test, then inspect bounded request metadata. Errors preserve operator input. Narrow layouts focus the inspector with a return action. API credentials stay in browser memory and never become shared infrastructure settings.

Use ordinary concrete modules. Do not build a generic backend trait until two supported engines require substitution. The initial configurable HTTP worker runs llama-server and a Rust test fixture through the same subprocess owner. Engines remain separate processes. Model-specific lifecycle locks never become global I/O locks. An inference lease keeps its worker busy until the upstream response finishes or is dropped.

The experimental config is explicit and separate from native Juiced state. It never reads or migrates production config implicitly. Initial resident estimates are operator-declared reservations, not measured hardware capacity. Exhaustion rejects admission without evicting another worker. The first slice does not claim the mature resource planner's adaptive slots, UMA accounting or fairness guarantees.

Exercise disabled models, CAS conflicts, persisted policy after restart, double load, crash/startup failure, timeout, request slot pressure, resident budget pressure, busy unload protection, scoped recovery and streaming/non-streaming disconnects. Use temporary directories and ephemeral listeners. Assert that failure releases the exact lease and unrelated workers remain alive.

Retain existing Python acceptance as an independent client-level oracle while porting behavior. Do not translate source assertions mechanically. Cross-platform CI and actual engine inference remain separate from fixture success.

## Offline runtime installation foundation

The runtime-package owner copies an exact local llama.cpp or whisper.cpp closure into private versioned storage. The offline flag shares configuration ownership with serving, so a live daemon excludes import. A bounded manifest reserves complete payload bytes before any package payload is created. Source and actual output hashes, roles, sizes and directory bindings are checked before the installed head is published. Completed files and directories become read-only. Existing installed packages are verified without repair or in-place writes.

Package identity binds canonical files, roles, declared sizes, builder/source/build labels and declared OS/architecture/ABI/compute paths. These labels and license/SBOM declarations do not establish compatibility, licensing acceptance, hardware or quality qualification. Control metadata stays outside the runtime closure. Identical complete files can be reused after interruption. Partial or conflicting bytes remain retained for inspection, with their full reservation charged. Corrupt, duplicate or unknown package state refuses without reset. Capacity rejects before unnecessary source hashing.

The initial interface is `lemond --config PATH --import-runtime-bundle IMPORT_SPEC_JSON`. It returns a verified BundleSpec for explicit profile selection and preserves the existing configuration. It neither starts a worker nor changes policy. Complete online acquisition, reference-safe package reclamation, full writer fencing and all platform cells remain required R4/R7 work. Selected profile references, retained history and launch ownership are described below. The POSIX implementation is separate from the unsupported-platform stub. Source/private-directory checks are point observations, not a complete outside-writer fence. Native, actual CLI and tiny real runtime/cache proof belong in VERIFICATION.md.

All four native prefixes enforce operator authority. Offline CLI and serving import share source verification, complete payload reservation, copy/seal checks and head publication. Inventory reads and startup remain non-creating. A serving import never selects a model runtime, changes policy or starts a worker. Networking and package deletion remain separate required work.

The package owner retains immutable records through shared snapshots. Index locks cover pointer access and binding acquisition only. Owned head publications preserve every existing record and charge, so retained workers can continue while the new head is written. Unknown writes retain both proposed and prior authority and pause changes. Directory scope includes all existing live storage roots. Source copying has one separate import owner. Accepted work survives caller disconnect and remains tracked through shutdown.
